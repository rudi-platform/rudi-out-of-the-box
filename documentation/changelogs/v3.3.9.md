# Opérations à effectuer pour le passsage à la 3.3.9

## Changements principaux
- Mise à jour de version environnement dans `.env`
- Évolutions de la configuration backend :
    - suppression de la clé `security.jwt.access.tokenKey` dans l'ensemble des microservices
    - ajout de `module.oauth2.issuers` (ACL)
    - ajout de `frontend.urlServer` (ACL)
    - ajout/correction de `module.anonymous` (API Gateway et Gateway)
- Montée de version Dataverse :
    - modifications Dockerfile/scripts
    - mise à jour des dépendances `maven/deps` (`.jar`)
    - mise à jour du contenu applicatif packagé (classes/fichiers embarqués)
- Mise à jour Solr :
    - schémas (`schema.xml` et fichiers liés)
    - index/tlog Solr mis à jour
- Suppression complète du dossier `image/solr/configbacker`

## Configuration backend
Dans tous les microservices (acl, apigateway, gateway, kalim, konsult, konsent, kos, projekt, selfdata, strukture):
- Suppression de `security.jwt.access.tokenKey`

Dans apigateway et gateway : 
- Ajout de de configuration `module.anonymous` pour la gestion des utilisateurs anonymes (gestion d'un accès direct anonymous pour certaines opérations)

Dans acl : 
- Ajout de la configuration `module.oauth2.issuers` pour la gestion des émetteurs OAuth2
- Ajout de la configuration `frontend.urlServer` pour la gestion des URLs de serveur frontend

## Dataverse montée de version et nouveaux champs
Passage de Dataverse v6.5 à v6.9 
- Générer la nouvelle image Dataverse
  - `.../image/dataverse/build-image.sh` génère automatiquement la nouvelle image Dataverse avec le nom attendu
- Générer la nouvelle image Solr
  - `.../image/solr/build-image.sh` génère automatiquement la nouvelle image Solr avec le nom attendu

Le champ datasetUpdateFrequency est rajouté aux jeux de données et doit donc être rajouté dans la configuration solr.
De plus le champ média est rendu optionnel.
Ces modifications sont portées dans les fichiers :
- `.../data/solr/solr-data/collection1/conf/schema.xml`
  - `<copyField source="rudi_dataset_update_frequency" dest="_text_" maxChars="3000"/>`
- `.../data/solr/solr-data/collection1/conf/schema_dv_mdb_copies.xml`
  - `<copyField source="rudi_dataset_update_frequency" dest="_text_" maxChars="3000"/>`
- `.../data/solr/solr-data/collection1/conf/schema_dv_mdb_fields.xml`
  - `<field name="rudi_dataset_update_frequency" type="text_en" multiValued="true" stored="true" indexed="true"/>` 
Si ces lignes ne sont aps présente dans vos fichier de configuration solr, il faut les ajouter.
Dans tous les cas, un clear du cache puis une réindexation sera nécessaire via les endpoint 
  - `http://dataverse.<ROOB_DATAVERSE>/api/admin/index/clear`
  - `http://dataverse.<ROOB_DATAVERSE>/api/admin/index`

## Suppression d'un jeu de données
La suppression d'un jeu de données entraîne maintenant l'envoi d'un mail à l'ensemble des réutilisateurs, ou membres de 
l'organisation à l'origine de la réutilisation utilisant ledit jeu de données.
Ce mécanisme demande de rajouter les propriétés suivantes dans le fichier [kalim.properties](../../config/kalim/kalim.properties)
```properties
freemarker.baseDirectory=chemin vers le dossier des templates

mail.smtp.host=host smtp
mail.smtp.port=port smtp
mail.smtp.auth=true si une authentification est requise, false sinon
mail.smtp.user=login smtp (si mail.smtp.auth=true)
mail.smtp.password=mot de passe smtp (si mail.smtp.auth=true)
mail.smtp.starttls.enable=true si le serveur smtp supporte TLS, false sinon
mail.from=email de l'expéditeur

email.urlServer=url du site (pour redirection dans les mails)
email.teamName=nom de l'équipe pour signature des mails
email.projectName=nom du projet (pour les entêtes de mail)
```
